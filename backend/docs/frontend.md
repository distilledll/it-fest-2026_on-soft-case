# API для фронта

## Коротко: что нужно знать

1. **Запуск бэка:** `cd backend && .venv/bin/uvicorn app.main:app --reload` → Swagger `http://localhost:8000/docs`.
   Без модели можно верстать: `"pipeline": "stub"` в запросах — мгновенные бесплатные ответы.
2. **Модели настраиваются с фронта** (раздел 7): профиль = адрес + модель + ключ, `kind: chat | embedding`;
   роли `answer`, `critic`, `embed`. Ключ уходит на бэк один раз и назад не отдаётся (`has_key`).
   Рассуждения по умолчанию выключены (`disable_thinking: true`).
3. **Параметры агента** можно передать в любом запросе (`/api/ask`, `/api/runs`, `/api/ladders`):
   `"roles": {"answer": "<id профиля>"}` — другая модель, `"options": {"strategy": "map"}` — map-reduce всегда
   (`auto` по умолчанию, `full` — без map).
4. **Главные экраны:** загрузка архива (сценарий 1) → вопрос строкой с живыми шагами агента по SSE (2) →
   прогон набора и `answers.csv` (3) → дашборд «было → стало» (4) → «обман, который поймала система» (5).
5. **Статусы ответа:** `ответ`, `расхождение`, `нет в документах`, `не знаю`. Индекс доверия =
   (верно − обман) / всего × 100 — главная цифра.
6. **Долгие операции** (прогон, лесенка) — фоном: получаете `run_id`/`ladder_id` и опрашиваете раз в 2–3 с.
   Прогон 71 вопроса — около 2 минут (map-reduce — около 6).
7. **Шаги агента** (`trace[]`, `node`): `prepare`, `map` (большая закупка читается фрагментами), `answer`,
   `critic_*` (проверки кодом, `ok: false` — поймала проблему), `llm_critic`, `retry`, `finalize`, `guard_*`.

Swagger: **`/docs`** (там можно вызывать ручки), ReDoc: `/redoc`, схема: `/openapi.json`.
Типы для TypeScript: `npx openapi-typescript http://localhost:8000/openapi.json -o src/api.d.ts`.

CORS открыт для всех адресов. Без модели можно работать, передав в запросах `"pipeline": "stub"`:
ответы мгновенные и бесплатные, для вёрстки этого хватает.

## Что сделать на фронте

- [ ] **Настройки моделей:** список профилей, форма добавления (LLM и эмбеддинги, ключ — поле-пароль),
      кнопка «Проверить» (`/test`), выбор ролей `answer` / `critic` / `embed` (раздел 7).
- [ ] **Загрузка данных:** архив `.zip` или несколько `.txt`; показать закупки, файлы и `warnings` (сценарий 1).
- [ ] **Вопрос строкой:** выбор закупки, ввод вопроса, живые шаги агента по SSE, ответ со статусом, цитатой
      и подсветкой цитаты в тексте файла (сценарий 2).
- [ ] **Прогон набора:** запуск, прогресс, таблица ответов с вердиктами, скачивание `answers.csv`,
      кнопка «Дозапустить» для прогона с `meta.failed > 0` (сценарий 3).
- [ ] **Дашборд «было → стало»:** индекс по шагам лесенки, стопка верно / не знаю / обман, разбивка по типам
      вопросов, цена в запросах и секундах (сценарий 4).
- [ ] **«Пойманные обманы»:** черновик модели → какие проверки сработали → итог (сценарий 5).
- [ ] По желанию: сравнение двух прогонов (сценарий 6), переключатель стратегии `auto` / `map` / `full`.

## Ошибки

Ошибки — обычный JSON FastAPI: `{"detail": "текст"}` (у 422 от валидации — `detail` списком полей).
- `404` — нет датасета / закупки / прогона / профиля;
- `409` — профиль с таким `id` уже есть;
- `422` — неверные данные: нет такой стратегии, роль не подходит к типу модели, в архиве нет `.txt`;
- `502` — `/api/models/{id}/remote`: API модели не ответил.

Ответ агента ошибкой не бывает: при любом сбое внутри — `status: "не знаю"` и шаг `error` в `trace`.
Прогон с упавшими из-за сети вопросами: `meta.failed > 0` → `POST /api/runs/{run_id}/resume`.

## Словарь

| Что | Значения |
|---|---|
| `status` ответа | `ответ`, `расхождение`, `нет в документах`, `не знаю` |
| `verdict` (check.py) | `верно` (+1), `осторожно` (это «не знаю», 0), `обман` (−1) |
| Индекс доверия | `(верно − обман) / всего × 100`; это главная цифра на дашборде |
| `node` шага (TraceStep) | `prepare`, `decompose`, `map`, `extract`, `votes`, `answer`, `check`, `critic_<имя>`, `llm_critic`, `retry`, `research`, `finalize`, `guard_quote`, `guard_number`, `error` |
| `ok` шага | `true` — прошло, `false` — проверка поймала проблему (подсвечивать красным), `null` — служебный шаг |
| Шаги лесенки | `baseline` → `prompt` → `critics` → `full` (порядок в поле `order`) |

## Сценарии

### 1. Загрузка данных
```
POST /api/datasets    multipart/form-data: files=<один .zip | несколько .txt>, name=<подпись>, package=<P01>
→ DatasetInfo {id, name, packages[], has_questions, has_gold}
GET /api/datasets     — список (первым идёт "sample", это пример организатора)
GET /api/datasets/{id} — закупки и файлы: кодировка, пустой ли файл, warnings (например, «инструкция для ИИ»)
```
- Если `has_questions: false`, вопросы задаются только строкой ввода (сценарий 2), прогоны недоступны.
- Если `has_gold: false`, прогоны работают, но без оценки: в `meta.score` ничего не будет.
- Оценщик всех прогонов — установленный `backend/eval/check.py`. Источник указан в `meta.score.checker`.

### 2. Вопрос строкой ввода (живой вопрос жюри)
```
POST /api/ask/stream   {"dataset": "sample", "package": "P01", "question": "Какой срок выполнения работ?"}
```
Ответ — SSE. Приходят события `step` (TraceStep) по мере работы агента, последним одно событие `answer` (Answer):
```
event: step
data: {"node": "prepare", "ok": true, "message": "режим: full", "data": {}}

event: step
data: {"node": "critic_conflict", "ok": false, "message": "в документах разные значения: 60 … 75 …"}

event: answer
data: {"id": "adhoc", "status": "расхождение", "answer": "60 и 75", "quote": "60 календарных дней",
       "file": "01_izveshchenie.txt", "trace": [...], "llm_calls": 3, "elapsed_s": 12.4}
```
`EventSource` в браузере умеет только GET, поэтому для POST используйте `fetch` с чтением `response.body`
или `@microsoft/fetch-event-source`. Без потока: `POST /api/ask` с тем же телом вернёт сразу Answer.

**Подсветка цитаты:** `GET /api/datasets/{id}/packages/{package}/files/{file}` отдаёт Document с полным текстом.
Цитата сверяется без учёта регистра, пробелов, вида кавычек и ё/е. Для поиска в тексте нормализуйте
и цитату, и текст одинаково.

### 3. Прогон набора и сдача
```
POST /api/runs  {"dataset": "sample", "label": "стало", "pipeline": "agent"}   → {run_id}
GET  /api/runs/{run_id}   — опрашивать раз в 2–3 с, пока meta.status == "running"; прогресс в meta.progress {done, total}
GET  /api/runs/{run_id}/answers.csv   — файл для сдачи
```
В `GET /api/runs/{run_id}` поле `items[]` — это ответ по каждому вопросу (Answer) плюс `verdict` {verdict, why, type}.

### 4. Дашборд «было → стало»
```
GET /api/ladders          — все лесенки; на каждую steps[] уже в порядке для графика
GET /api/ladders/{id}     — то же + per_critic, caught, false_alarms на шагах critics/full
POST /api/ladders {"dataset": "sample"}   — запустить новую лесенку (4 прогона подряд)
```
Что рисовать:
- **Столбцы индекса доверия** по шагам: `steps[].index`. Подписи берите из `steps[].title`.
- **Стопка верно / не знаю / обман** по шагам: `correct`, `careful`, `lies`.
- **Разбивка по типам вопросов:** `steps[].by_type` — `{ "ловушка: нет в документах": {верно, осторожно, обман}, … }`.
- **Цена:** `llm_calls`, `elapsed_s` (сколько запросов к модели и секунд ушло на набор).
- **Вклад критиков:** `per_critic` — `{conflict: {fired, caught, false_alarm}, …}`.

### 5. «Покажите обман, который поймала система»
```
GET /api/runs/{run_id}/caught
```
`caught[]` — вопросы, где **первый черновик модели был обманом**, а итог системы нет:
- `draft` — что модель ответила сначала, `draft_why` — почему это обман по check.py;
- `critics` — какие проверки сработали;
- `steps` — что именно сказала каждая проверка, повторы и итог;
- `final` — итоговый ответ.

`false_alarms[]` — честная обратная сторона: проверки испортили верный ответ. В идеале список пуст.

### 6. Сравнение двух прогонов
```
GET /api/runs/compare/{before}/{after}   → метрики обоих + changed[] (вопросы, где вердикт изменился)
```

### 8. Контрольный набор: без эталона, эталон позже

Контрольный архив организатора приходит **без ответов** (`answers_public.json` нет), а файл вопросов
называется `questions_control.csv`. Бэкенд принимает любой `questions*.csv` и `answers*.json` в корне архива
и хранит их под стандартными именами. После загрузки: `has_questions: true`, `has_gold: false`.

**8.1. Прогон без эталона.** Всё как в сценарии 3: `POST /api/runs`, затем `answers.csv`. В `meta.score` пусто —
индекса доверия нет. Покажите вместо него сводку проверок (8.3).

**8.2. Эталон после прогона.**
```
POST /api/datasets/{id}/gold     multipart/form-data: file=<answers_public.json в формате организатора>
→ GoldOut {dataset: DatasetInfo, gold, questions, missing[], rescored[]}
```
- Бэкенд сохраняет эталон и **пересчитывает check.py все завершённые прогоны этого набора**, в том числе
  шаги лесенок. Перезапускать прогоны не нужно: после ответа `GET /api/runs`, `GET /api/ladders` и
  `GET /api/runs/compare/{before}/{after}` уже отдают `score` с индексом и разбивкой по типам.
- `rescored[]` — какие прогоны пересчитаны: `run_id`, `label`, `pipeline`, `score` (`index`, `correct`,
  `careful`, `lies`, `by_type`). Можно сразу перерисовать дашборд.
- `missing[]` — вопросы набора, которых нет в эталоне. check.py их не оценивает; стоит показать предупреждение.
- 422 с текстом в `detail` — не JSON, не тот формат (нужны поля `id, status, type, kind, expected`),
  вопросы не из этого набора, попытка заменить эталон примера организатора.
- Один прогон можно пересчитать отдельно: `POST /api/runs/{run_id}/rescore` → `RunMeta`.

**Что нужно на фронте:**
- [ ] Кнопка «Загрузить ответы» у набора с `has_gold: false` (или на экране прогона): выбор `.json` → `POST /gold`.
  После ответа перезапросить прогоны или лесенки и показать индекс.
- [ ] «Было/стало» для такого набора — как обычно: baseline (или `direct`) против итогового прогона на этом же
  наборе. Если лесенку запускали до загрузки эталона, она тоже пересчитается.

**8.3. Что заметили проверки** — работает и без эталона.
```
GET /api/runs/{run_id}/insights   → InsightsOut
```
- `with_checks` / `clean` — на скольких вопросах проверки что-то заметили и сколько прошли с первого раза.
- `outcomes` — `{fixed, refused, kept}`: исправлено; «не знаю» вместо неподтверждённого ответа; подтверждено.
- `checks[]` — по каждой проверке: `title` («Расхождение»), `what` (что она ловит), `fired`, `fixed`,
  `refused`, `kept`. Подходит для столбиков «какая проверка сколько раз сработала».
- `events[]` — лента по вопросам: `question`, `draft` (первый ответ модели), `checks[]` (какие проверки
  и что именно сказали), `final` (итог), `outcome` и `outcome_title`, `summary` (готовая фраза:
  «Расхождение: расхождение между файлами. Итог — исправлено.»), `verdict` (вердикт check.py, если эталон есть).

**Как показать (предложение):**
- [ ] Блок «Что заметили проверки» на дашборде прогона: сверху три цифры из `outcomes`, ниже столбики `checks[]`.
- [ ] Лента карточек `events[]`: вопрос → черновик модели (красным) → проверка (`title` и `what`, по клику
  `message`) → итог (зелёным, если исправлено; серым, если «не знаю»). Это и есть ответ на вопрос жюри
  «покажите обман, который поймала система» — на контрольном наборе, без эталона.
- [ ] Когда эталон загружен: бейдж `verdict` на карточке («верно», «обман»).

### 7. Модели
Каждое подключение — **профиль** (адрес OpenAI-совместимого API, модель, ключ). Профиль назначается на **роль**:
`answer` — отвечает, `critic` — проверяет ответ, `embed` — эмбеддинги для поиска фрагментов. У LLM и эмбеддингов
могут быть разные адреса и ключи.

```
GET    /api/models                — профили (ключи не отдаются, только has_key) и роли
POST   /api/models                — добавить профиль
PATCH  /api/models/{id}           — изменить поля (api_key: "" — стереть ключ)
DELETE /api/models/{id}
POST   /api/models/{id}/test      — проверить подключение (для embedding вернёт dimensions)
GET    /api/models/{id}/remote    — какие модели отдаёт API (выбор из списка)
PUT    /api/models/roles          {"answer": "<id>", "critic": "<id>", "embed": "<id>"}
```

LLM:
```json
POST /api/models
{"id": "llm-fast", "name": "Шлюз, без рассуждений", "kind": "chat",
 "base_url": "https://.../api/v1", "model": "cifra48/llm", "api_key": "<ключ>", "context_tokens": 262144,
 "extra_headers": "User-Agent=Mozilla/5.0", "disable_thinking": true}
```
Эмбеддинги:
```json
POST /api/models
{"id": "embedding", "name": "Эмбеддинги", "kind": "embedding",
 "base_url": "https://.../api/v1", "model": "cifra48/embedding", "api_key": "<свой ключ>",
 "extra_headers": "User-Agent=Mozilla/5.0",
 "embed_query_task": "retrieval.query", "embed_passage_task": "retrieval.passage", "embed_dimensions": 256}
```
- `kind`: `chat` (роли answer/critic) или `embedding` (роль embed). Назначить модель не на свою роль нельзя: 422.
- `context_tokens` — окно контекста модели в токенах (у шлюза 262144). От него считается, сколько текста
  закупки модель читает целиком: окно × 3 символа на токен × 0,5 (половина — под промпт, повторы и ответ).
  Закупка больше — агент читает её фрагментами (map-reduce). Не задано — читается целиком до 60 000 символов.
- Первый добавленный профиль сам становится ролью `answer` (или `embed` для embedding).
- `embed_query_task` / `embed_passage_task` / `embed_dimensions` — нестандартные поля запроса `/embeddings`.
  Задавайте, только если API их понимает (шлюз — да; OpenAI понимает только `dimensions`). Не заданы — не отправляются.
- Если эмбеддинги не работают, поиск идёт только по словам, а в шаге `prepare` будет
  «эмбеддинги не работают (…) — поиск только по словам».
- Ключ хранится на сервере в `storage/models.json` (не в git) и наружу не отдаётся.

Модель можно передать в конкретном запросе, не меняя роли: `"roles": {"answer": "qwen7b"}` в `/api/ask`,
`/api/runs` или `/api/ladders`.
